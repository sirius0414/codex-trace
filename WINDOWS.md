# Native Windows Support and Validation

[English](WINDOWS.md) | [简体中文](WINDOWS.zh-CN.md)

The target environment is Windows 10/11, a local NTFS volume, and native Codex; WSL is not required. Start Codex and the terminal as a regular user. Running as administrator is unsupported: an elevated token may make the Administrators group the owner of new files, which the plugin rejects instead of taking ownership or relaxing protections. Community installation requires Git, uv, and Codex CLI 0.153.0 or a later compatible version; uv manages Python 3.14.2. Initial preparation, dependency changes, or cache misses require network access. The optional ZIP installer and source workflow below require local Python 3.14+ (including `compression.zstd`). Follow the [community installation guide](INSTALL.md#community-marketplace-installation), including its network access and runtime preparation requirements. Regular users do not need Node.js/npm; only the source workflow below requires them.

For actual community-channel native results, see the corresponding version's [GitHub Release validation records](https://github.com/sirius0414/codex-trace/releases/tag/v0.2.1). The implementation notes, macOS checks, and simulations below do not establish Windows success.

GitHub Windows runners use administrator tokens. The CI diagnostic wrapper starts a new test subprocess, verifies that its TokenId differs from the parent's and its TokenUser matches, then normalizes only the child's default TokenOwner to that user. It restores the child token in a finally block and checks that the parent token remains unchanged. It neither changes existing file ownership nor relaxes the product's SID/DACL checks. This exercises native Windows APIs while retaining administrator privileges; it is not regular-user desktop acceptance, and elevated product startup remains unsupported. The wrapper's presence alone does not establish that a CI run passed.

## Source development and local packaging

Prepare the development dependencies in PowerShell. Paths may contain Chinese characters and spaces; you do not need to activate the virtual environment or change the execution policy:

```powershell
py -3.14 -m venv .venv
& .\.venv\Scripts\python.exe -m pip install -r requirements.lock
npm ci --ignore-scripts
npm run build

# Confirm the actual native Codex path; the script can also recognize codex.cmd from a standard npm installation.
$codexExe = 'C:\Program Files\Codex\codex.exe'
npm run plugin:update -- --prepare-only --python "$PWD\.venv\Scripts\python.exe" --codex "$codexExe"

# Browser development server; open the local address printed when it is ready.
npm run dev:browser:start -- --python "$PWD\.venv\Scripts\python.exe" --codex "$codexExe"
npm run dev:browser:status
npm run dev:browser:stop
```

`--prepare-only` generates and validates artifacts only. For subsequent installation, use the output directory as described in the [README](README.md#install-update-and-uninstall). The local package generated by this development workflow contains absolute interpreter and Codex paths. It cannot be copied directly between macOS and Windows; rebuild it after moving the runtime environment. For release ZIPs distributed to other users, the installer generates these paths on the target machine; see the [installation guide](INSTALL.md). Startup in this prepared development or installer environment does not download dependencies; the community uv workflow has the network behavior described above.

The npm development entry points use `scripts/run_python.mjs` to prefer `CODEX_TRACE_PYTHON` or the repository's `.venv` before searching for a system Python. On Windows, the wrapper recognizes only the standard npm installation layout and locates the native `codex.exe`; for a custom `.cmd`/`.bat` wrapper, pass the actual executable instead. npm builds run the npm CLI through Node, with user directories and arguments passed as separate argv entries. The background development server requires PowerShell/CIM to read process creation times and command lines. If identity cannot be established or stopping times out, it retains the record and reports an error.

| Data | Default Windows location |
| --- | --- |
| Read-only task sources | `%USERPROFILE%\.codex\sessions` and `archived_sessions`; overridable with `CODEX_HOME` |
| Derived index, preferences, receipts, and temporary ZIPs | `%LOCALAPPDATA%\codex-trace\index` |
| Final exports | `%USERPROFILE%\Downloads\Codex Trace` |

The parent `Downloads` directory must already exist. Local `CODEX_TRACE_STATE_ROOT` and `CODEX_TRACE_EXPORT_ROOT` settings can configure the state and export roots; tool arguments and the frontend cannot specify destinations. Production frontend receipts still require the `Downloads\Codex Trace` suffix; isolated tests can inject temporary directories. File sharing conflicts on Windows may cause an operation to fail. Release the conflicting handle, then reconcile the same request; a timeout or `unknown` result must not lead to a new save request.

## Platform boundaries and guarantees

`backend/codex_trace/platform/` handles operating-system differences. Raw trajectory analysis, domain projections, the export state machine, and the frontend remain shared.

| Boundary | macOS | Windows |
| --- | --- | --- |
| Source reads and directory traversal | `dir_fd`, `O_NOFOLLOW` | `CreateFileW` rejects reparse points at every level; directory handles retain ancestors and restrict write/delete sharing; volume GUID paths are used internally |
| Private state | Ownership checks and 0700/0600 modes | Owner SID checks; protected current-user/SYSTEM DACL; SQLite sidecar files may inherit an equally restricted ACL |
| Concurrency and idempotency | `flock` + SQLite/CAS receipts | `LockFileEx` + the same SQLite/CAS receipts; lock files remain in place |
| Final publication | Hard link without overwriting | Handle-relative `NtSetInformationFile(FileLinkInformation)`, with replacement of existing names prohibited |
| Content verification | File flush, hash, and identity readback | File flush, hash, and identity readback; the write handle is closed before the frozen snapshot is reopened read-only |
| app-server pipes | Nonblocking selector | Bounded queues and dedicated reader/writer threads with a shared request deadline; shutdown uses retained thread handles to cancel synchronous I/O before reclaiming the connection |
| Source changes | kqueue + polling | Polling fallback with intervals of at most 250 ms; each read still validates identity and scope |

Windows file protection uses real ACLs and native file identities. It does not treat `chmod`, `Path.resolve()`, or removal of Unix flags as equivalent guarantees. Ordinary file descriptors remain in binary mode. Offset reads use `ReOpenFile` with an independent file pointer, without moving the caller's pointer or that of its `dup`. Raw sources are opened for reading only, without write locks or tightened source ACLs. The app-server itself may still maintain its own runtime cache.

Existing POSIX export paths remain valid. The Windows default is `%USERPROFILE%\Downloads\Codex Trace\`; an example with Chinese characters and spaces is `C:\Codex Trace 测试\导出记录\codex-trace-….zip`. The schema and both frontend export entry points share test fixtures that reject drive-relative paths, UNC paths, device namespaces, ADS, traversal, reserved device names, and trailing dots/spaces. The backend also checks actual directory and file identities; frontend syntax checks alone cannot establish safety.

Source, state, and export directories on network volumes, UNC shares, junctions, symbolic links, or other reparse points are unsupported, including user directories redirected through those mechanisms. FAT/exFAT, ReFS, cloud placeholder files, and every long-path combination have not been validated. Windows provides no directory `fsync` equivalent usable by this adapter: file-content flushing and readback are checked, but directory-entry durability after sudden power loss is not guaranteed. Pending receipts must still be reconciled using the original request. Administrators and SYSTEM retain their operating-system privileges.

Native API references: [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex), [FILE_LINK_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_link_information), [ReOpenFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-reopenfile), and [CancelSynchronousIo](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio).

## Runnable regression checks

Windows PowerShell:

```powershell
$env:PYTHONUTF8 = '1'
$env:PYTHONPATH = "$PWD\backend;$PWD\tests"
& .\.venv\Scripts\python.exe -m unittest discover -s tests -v
& .\.venv\Scripts\python.exe contracts/generate_types.py --check
npm test
npm run build
git diff --check

# Run only the platform core checks (still using real processes and filesystems on the current host).
& .\.venv\Scripts\python.exe -m unittest test_platform_filesystem test_platform_runtime test_platform_pipes test_platform_scripts -v
```

`test_platform_runtime` covers paths with Chinese characters/spaces, fragmented UTF-8 pipes, read timeouts, write backpressure, thread/subprocess cleanup, cross-process locks under spawn, two processes competing to save the same candidate without overwriting, byte-for-byte raw ZIP verification, and idempotent receipt recovery across restarts. `test_platform_pipes` checks blocked I/O cleanup while another process owned by the user continues holding a pipe. `test_platform_filesystem` adds Windows-specific checks for junctions, pinned directories, exclusive file handles, SID/DACL, and SQLite sidecars. The path-selection simulations in `test_platform_scripts` are explicitly marked as simulations; CIM, Windows argv, and Job Object cases run only on native Windows.

Older FIFO and Unix chmod attack cases run only on applicable platforms; Windows counterparts use native file-sharing, ACL, and handle semantics. If the Windows user lacks permission to create symbolic links, only link cases requiring that permission are skipped; junction cases run independently. Every skip must remain visible in the report.

## Historical validation record (2026-10-28)

The development machine was macOS, with no physical Windows machine or Windows VM available. The implementation was based on local commit `50ab87f`. An attempt to fetch the latest remote code lacked GitHub HTTPS credentials, so additional remote commits could not be ruled out. The working tree was clean at the start.

- Baseline before changes: 478 Python tests and 288 frontend tests passed, along with the build and contract-generation checks.
- Full regression after changes: 519 Python tests total, with 506 passed and 13 Windows-only checks skipped; 291 frontend tests passed. The build, contract/type consistency, Python/JavaScript syntax, and `git diff --check` passed. The Python regression run emitted no unclosed-resource warnings. Full logs were retained locally at `/tmp/codex-trace-windows-*.log`.
- Final macOS packaging and isolated-cache validation: 45 checks passed. The report was `build/windows-compat-final-buqu_rz5/verification.json`, with `desktopInstalled=false`, `hostUiVerified=false`, and `taskDataRead=false`. Validation used synthetic tasks and temporary directories, without installing the real plugin or reading real tasks.
- macOS tests, simulated Windows branches, and Python compilation checks do not establish that native Windows tests passed.

At that time, the full checks above still needed to run on Windows, followed by validation of local NTFS ACLs/inheritance, junction/ancestor replacement, file-sharing conflicts, multi-process saves of the same request and crash recovery; discovery, installation, updates, and rollback through the real Codex CLI; the desktop MCP entry point and exports to Chinese-character paths; and development-server start/status/restart/stop plus child-process cleanup after abnormal exit. No real plugin update or desktop entry-point operation had been performed as part of that validation.
